## Summary

Deliver a static, offline, responsive Three.js r128 browser viewer for the portable four-cartridge drum and deterministic scan/cap/refill demo. The main viewer also gets an independent, default-off, visual-only “Show dimensions” overlay: it reads canonical dimension records and named recipe/derivation values, preserves their provenance and caveats, and never affects the assembly or the FR-034 52-instance export. The controlling dispensing-station geometry and sequence are the two-gate requirements in [spec.md](spec.md), not the earlier scan-derived single-gate interpretation. Keep the upper sliding separator and shared lower floor as distinct mechanisms with a strict two-way interlock. The chamber is empty at rest; the bottom pill of a later explicitly filled stack is staged only after the upper blade opens and that pill falls onto the still-closed lower tongue. Preserve pill identity as the blade closes into the seam, lifts pills 2+ about 1 mm, dwells fully closed for 0.3 s, then releases the same pill vertically through the outlet and waits until visibly clear before spring-closing.

Fresh load and safe reset show exactly RED, BLUE, GREEN and ORANGE compartments, all inserted and empty, caps closed/locked, and no pill actors. Explicit Fill may later create fictional assumed inventory (up to five actors in each compartment). The main-scene scanner is an independently show/hideable visual subsystem with its own local controller and fixed fictional fixture map: 5012345678900→RED, 5012345678917→BLUE, 5012345678924→GREEN, 5012345678931→ORANGE. A supported scan to an available zero-count, no-container compartment follows initial placement: package-in → read/beam → result → matching-only placement → package-out → open only the matching simulated lid. A supported rescan to an available zero-count compartment whose same-color container is already present follows separate recognition: package-in → read/beam → result identifying/reusing that existing container → package-out → open only its matching lid; it performs no placement or count mutation, leaving Fill explicit. Positive-count, absent/removed, mismatched, busy, open/unlocked or otherwise unavailable targets, and unsupported/unmapped/unknown/ambiguous/invalid inputs remain refusals with no placement, lid opening or compartment-state mutation. Feature 004 remains a separate subsystem lab; Feature 003 imports or shares none of its state or fixtures.

Use one versioned, source-attributed concept geometry JSON for the browser data bundle and stdlib Python 3MF generator. Vendor Three.js r128 UMD and its MIT notice locally; use no CDN, npm, server, network or optional Python GUI dependency at runtime. Export the complete parked portable concept as one right-handed millimetre 3MF Core assembly and staged/hash-checked manifest. Preserve the Python simulator, persisted records and Feature 002 2D player; retire the run-driven `animate --3d`/pyglet viewer.

### Dimension-annotation overlay (FR-031 / SC-019)

The main viewer adds an accessible “Show dimensions” checkbox, initially unchecked and independent of cap, part-label, scanner, and dispensing-mechanism visibility controls, plus a dimension-group selector shown only while dimensions are enabled. The selector displays a focused group at a time (assembly, color-specific cartridges/channels/caps and blades, lower tongue, pin/slot, actuator linkage, outlet/tray) so dimension callouts do not blanket the assembly. It owns dedicated fixed and rotating Three.js overlay groups containing thin, straight white/grey measurement strokes, per-value straight guide leaders, and value sprites; group visibility is not parented under a hideable physical component, ordinary part labels, or scanner visuals. Numeric labels sit on a clear outside-the-mechanism callout rail, never over or buried inside the physical assembly, and each label has its own straight leader to the measured feature. Toggling the dimensions control or changing the category changes only overlay visibility. It does not call or mutate the demo controller, alter camera transforms, or change visibility/transforms of physical parts, existing labels, scanner visuals, caps, pills, or scan actors. The overlay remains presentation-only and excluded from canonical components and all export paths.

Implement a deterministic renderer-independent annotation catalog in `docs/visualizer/dimension-annotations.js`, loaded as a local classic script by the viewer and browser harness. It maps each displayed feature to an existing canonical `dimensions[]` ID, an explicitly named `component_recipes[]` parameter, or an existing versioned derivation rule; each record carries component/group association, a numeric value only when available, unit, source provenance, verification status, caveat, and source frame/anchor/axis metadata. Its line endpoints are constructed by the renderer from those source values, canonical feature datums, and explicit presentation offsets before applying the canonical-to-Three `(x,z,−y)` mapping. Rendered mesh bounds, `Box3`, screen-space extents, or visual estimates are never a source for a dimension value, measurement endpoint, or missing-value substitute. Recipe-derived dimensions must be labeled “recipe-defined”/“assumed” as applicable; every numeric callout carries mm units, its source provenance, `NOT VALIDATED`, and the relevant caveat. Missing values remain a nonnumeric “unspecified” notice, not a line with guessed endpoints. The browser harness tests catalog coverage and metadata without WebGL; foreground rendering tests exercise the actual Three.js overlay.

Use `THREE.LineSegments`/`THREE.BufferGeometry` for dimension, extension, and tick/arrow strokes, and `THREE.Sprite` labels backed by local canvas textures (reusing the existing sprite pattern). Keep annotation objects retained rather than rebuilding them per frame. Use predictable callout offsets and group placement around known features so labels remain associated during orbit and do not depend on mesh-bound fitting. Display one selected cluster at a time for station/housing footprint (44 × 74 mm, nominal, not a complete device envelope); central post/drum; cartridge/channel/caps; the four separate station blades/wedges/endpoints; lower tongue; pin/slot; actuator linkage; or outlet/tray. Use per-station blade annotations rather than implying one blade is shared. Keep units, provenance, status, and caveats on each displayed annotation. Tray height and all other absent dimensions remain explicitly unspecified. The selector must not provide a mode where all annotation labels stack over one another at once.

Crowded views are handled by compact grouped callouts, short leader strokes and labels that retain feature identity; longer source/caveat text remains associated with the same annotation rather than being dropped. The master checkbox hides/restores all dimension lines and their labels together while preserving their source values and deterministic layout. Dimension geometry must not obscure or replace physical parts, and no overlay object becomes a physical 3MF instance.

#### Canonical datum and frame conversion

- Right-handed millimetres: +X right, +Y depth/back, +Z up. Station datum S=(0,0,0); post/drum axis XY=(0,15); z=0 is the closed tongue upper face. A Three.js-only display conversion may map canonical `(x,y,z)` to `(x,z,−y)`; canonical JSON, Python geometry and 3MF remain in canonical coordinates.
- This station-root frame replaces the former axle-centered placement root. Translate prior axle-centered XY locations by +15 mm in canonical Y; X and Z do not change. It is a coordinate/datum conversion, not a physical geometry change. The old socket formula generated [0,−15], [15,0], [0,15], [−15,0]; it is superseded, not treated as an alternate valid assembly.
- Drum socket centers for $a_i=i\pi/2$ are $[15\sin(a_i),15-15\cos(a_i),27.1]$, in RED, BLUE, GREEN, ORANGE order: [0,0,27.1], [15,15,27.1], [0,30,27.1], [−15,15,27.1]. The 15 mm is the cartridge/socket-center radius, distinct from the canonical drum recipe's 8 mm outer radius.
